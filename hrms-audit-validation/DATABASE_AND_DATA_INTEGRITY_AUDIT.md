# Database Schema & Data Integrity Audit

**Vulnerability Classification:** P1 / P2 (Integrity, Concurrency, and Repudiation Risks)  
**Target:** Prisma 6 Schema (`prisma/schema.prisma`) and PostgreSQL 16 Persistence Layer  
**Key Affected Models:** `Company`, `User`, `Employee`, `AuditLog`, `Attendance`, `LeaveRequest`, `Payroll`  

---

## 1. Relational Model Inventory & Schema Topology

The database schema comprises **27 relational models** organized into four functional domains:

```
[Core Multi-Tenancy] ──> Company, Department, User, Employee, EmployeeCompanyAssignment, UserCompanyScope
[HR Operations]      ──> Attendance, LeaveType, LeaveRequest, Payroll, DailyWorkReport, WorkReportComment
[Talent & Performance]──> JobOpening, JobApplication, PerformanceReview, KPI
[Institute Pipeline] ──> Student, Course, Batch, StudentEnrollment, FeePayment, Assessment, AssessmentResult, Placement
[System & Audit]     ──> Announcement, Notification, AuditLog
```

## 2. Integrity Constraints & Concurrency Safeguards

### A. Compound Unique Constraints
The schema effectively leverages compound unique constraints to preserve data integrity and idempotency:

| Model | Constraint Fields | Business Invariant Enforced |
|---|---|---|
| `Attendance` | `[employeeId, date]` | Prevents multiple attendance records for an employee on a single day. |
| `Payroll` | `[employeeId, month, year]` | Prevents duplicate salary slips for an employee in the same pay period. |
| `DailyWorkReport` | `[employeeId, date]` | Limits daily EOD submissions to one primary report per employee per day. |
| `EmployeeCompanyAssignment` | `[employeeId, companyId]` | Prevents redundant company assignment links for shared employees. |
| `UserCompanyScope` | `[userId, companyId]` | Guarantees uniqueness of administrative tenant delegations. |
| `LeaveType` | `[companyId, name]` | Enforces unique leave type naming within a given company. |
| `StudentEnrollment` | `[studentId, batchId]` | Prevents duplicate student enrollments in the same cohort batch. |

---

### B. Indexing Coverage
Targeted indexes exist on critical foreign keys:
- `Attendance`: `@@index([companyId])`, `@@index([date])`, `@@index([companyId, date])`
- `Payroll`: `@@index([employeeId])`, `@@index([month, year])`
- `LeaveRequest`: `@@index([employeeId])`, `@@index([leaveTypeId])`
- `AuditLog`: `@@index([userId])`, `@@index([action])`, `@@index([createdAt])`

*Assessment:* Query lookups filtered by company, employee, and date ranges benefit from index scans rather than full table sequential scans in PostgreSQL.

## 3. Critical Integrity Finding: Audit Trail Repudiation via Cascade Deletion

In `prisma/schema.prisma:459-472`:
```prisma
model AuditLog {
  id        String   @id @default(cuid())
  userId    String
  action    String
  entity    String
  entityId  String?
  meta      String?
  createdAt DateTime @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
  @@index([action])
  @@index([createdAt])
}
```

### Risk Analysis
1. The relationship between `AuditLog` and `User` specifies `onDelete: Cascade`.
2. If a user record is deleted (e.g., during administrative cleanup or employee de-provisioning), **all audit trail entries generated by that user are permanently erased from the database**.
3. **Repudiation Vulnerability:** A rogue administrator could perform unauthorized actions (e.g. altering salary, exporting data, or tampering with records) and subsequently delete their user account or have it purged, completely eliminating forensic evidence of their misconduct.
4. **Remediation:** Remove `onDelete: Cascade` on `AuditLog`. Set `userId String?` with `onDelete: SetNull` or `onDelete: Restrict`, preserving immutable audit logs regardless of actor lifecycle events.

## 4. Deletion Cascade & Dependency Graph Management

Prisma defaults to `onDelete: Restrict` unless specified. Because foreign keys span across 20+ tables referencing `Company`, `Employee`, and `User`, a naive `prisma.company.delete()` operation fails immediately due to foreign key violations.

### Verification of Hard-Delete Implementation (`src/app/api/companies/[id]/delete/route.ts`)
The company deletion controller executes an explicit 18-step reverse-dependency deletion sequence wrapped in an atomic `db.$transaction`:

1. Unassign shared employees (`employeeCompanyAssignment.deleteMany`)
2. Delete performance reviews & KPIs
3. Delete job applications & openings
4. Delete daily work report comments & reports
5. Delete payroll records
6. Delete leave requests & leave types
7. Delete attendance records
8. Delete department records
9. Delete company announcements
10. Unlink student placements, results, assessments, fee payments, and batches (for institute types)
11. Purge exclusive employees and users
12. Delete company row

*Assessment:* The manual reverse-dependency traversal within an atomic transaction is **structurally sound and prevents orphaned database records**, compensating for the absence of database-level cascade rules.

## 5. PostgreSQL vs SQLite Portability

The codebase was migrated from SQLite to PostgreSQL 16:
- **Enum Representation:** SQLite lacks native enums; Prisma models maintain string types with runtime TypeScript string union validation (`src/lib/constants.ts`). This remains portable.
- **Auto-Increment vs CUID/UUID:** Models consistently utilize `@default(cuid())` or `@default(uuid())`, avoiding engine-specific sequence behaviors.
- **Connection URL:** Configured via `DATABASE_URL` in `.env`, operating cleanly inside the Docker PostgreSQL container.
